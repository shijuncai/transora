## 3. 验收数据

### 3.1 字符召回（对 PDFKit 交叉验证）

方法：逐页把我们的 IL 文本（段落 + 表格单元格）与 `PDFPage.string` 做**字符多重集**比较，  
算「交集 / PDFKit 字数」。用多重集而不是序列，是因为 PDFKit 的输出顺序不等于阅读顺序，  
比序列会把「顺序不同」误判成「丢字」。

| 文档                 | 页数  | PDFKit 字符 | 我们      | 召回         |
| ------------------ | --- | --------- | ------- | ---------- |
| Paxlovid 说明书       | 40  | 32,828    | 32,852  | **0.9999** |
| 语法俱乐部              | 340 | 222,015   | 222,057 | **1.0000** |
| Python 编程快速上手      | 409 | 395,465   | 396,012 | **0.9997** |
| Python 核心编程（第 3 版） | 661 | 567,908   | 569,549 | **0.9993** |
| 装配自动化与产品设计         | 440 | 0         | 0       | 扫描件，无文字层   |

「我们」偶尔比 PDFKit 多几个字符，是空格与全角标点的计法差异，不是多提取了内容。

### 3.2 表格结构

合成基准：3 种边框样式（全网格 / 无外框 / 只有外框+竖线）× 7 种行数（2–8）× 5 种列数（2–6），共 105 例。

```
合成表格 105 例：检出 105（100.0%），结构与真值完全一致 105（100.0%）
```

真实文档：《Python 核心编程》检出 134 张表，人工抽查第 30 页两张（4×2 的「模式/匹配字符串」  
与 17×3 的「表 1-1 常见正则表达式符号」），**行列数与页面完全一致**。

> 说明：架构文档写的验收线是「表格检出召回 ≥ 0.85」。这个数字在合成集上达成（1.00），  
> 但**没有人工标注的真实语料**，所以我不宣称真实文档也是 0.85——  
> 只给「抽查一致」这一条可复核的证据。

## 4. 踩到的坑

### 4.1 CMap 的 codespace 不能信，码长由字体决定

某本书的 Monospace 子集字体，`/ToUnicode` 里全是 `<20> <0020>` 这样的**1 字节码**，  
但 codespace 写的是 `<0000> <FFFF>`（2 字节）。

我按 codespace 切字节 → 两个字节拼成一个码 → 561 个字形里 **471 个取不到 unicode**，  
整本书 136 页召回只有 0.3–0.5。

修法：**只有 Type0 才参考 CMap 的 codespace；简单字体一律按 1 字节切**。  
码长是字体的属性，不是 CMap 的属性——生成器写 codespace 时普遍不严谨。

这条修完，召回从 0.866 直接回到 0.9997。

### 4.2 字体没 `/ToUnicode` 也没嵌入，只能靠预定义编码表

同一本书另有 136 页用 ArialMT / TimesNewRomanPSMT：**既无 `/ToUnicode`，也没嵌入字体文件**，  
但声明了 `/Encoding /WinAnsiEncoding`。

这时唯一可靠的信息就是编码表本身。补了 WinAnsi（CP1252）/ MacRoman / Standard 三张表后，  
这些页从「一堆乱码」变成正确文本。

### 4.3 同一基线上的两个表格单元格被并成一行

|                                       |      |        |                              |
| ------------------------------------- | ---- | ------ | ---------------------------- |
| 表头「药品类                                | 类内药物 | 对浓度的影响 | 临床评论」四个词在 PDF 里是同一基线的四段 run。 |
| 最初的按基线聚会把它们并成一条横贯整页的假行                |      |        |                              |
| （`药品类类内药物对浓度的影临床评论`），于是整行文字都落进了中间那一格。 |      |        |                              |

修法：按基线分组后，再按**水平间隙**切一刀（阈值 1.6em 且不低于 12pt）。  
正常词间距在 1em 以内，栏间距通常 ≥1.5em，正好分开。

### 4.4 一条横跨两栏的坏行，把整页判成单栏

上面那个 bug 的余波：左栏最后一行和右栏第一行的间隙只有 24pt，  
被 2.5em（26pt）的阈值判成同一行，于是这条「行」横跨两栏；  
而分栏检测当时是按**水平区间重叠**聚类的——一条跨栏行就把两栏连成了一栏。

两处都改了：

1. 阈值从 2.5em 收到 1.6em；
2. 分栏检测改成按**行首 x 直方图**聚类（容差取页宽的 6%），跨栏行只是没归到任何栏，  
   不再影响聚类结果。

顺带发现容差取 3pt 时，缩进的项目符号会分出假栏（实测一页切出 4 个簇，分栏直接失败），  
所以容差必须按页宽比例取。

### 4.5 「至少 2 个交点」把稀疏表格筛没了

表格线筛选最初用「交点 ≥ 2」排除装饰线。  
但**无外框的表格只有 1 条内横线**，此时每根竖线也只与它相交一次 → 整张表被筛空。  
这个 bug 让「无外框」这一类在合成基准上全部失败（89.5%）。

改成按**跨度占比**筛（横线长度 ≥ 区域宽度的 40%，竖线同理），合成基准随即 100%。

### 4.6 单元格文字必须按 run 归属，不能按行

相邻两列的文字在 PDF 里可能是紧挨着的（列边界就是文字起点），  
按「行」归属会把右列的字并进左格。改成按字形 run 的中心点归属后，  
药品表的每格内容才对上。

### 4.7 JSON 里的 `/` 被转义

`JSONSerialization` 默认把 `linguanova.il/1` 写成 `linguanova.il\/1`，  
不但文本匹配失效，人也读着别扭。加 `.withoutEscapingSlashes`。

## 5. 已知边界（不要当成 bug 报）

| 项                              | 状态与理由                                                                             |
| ------------------------------ | --------------------------------------------------------------------------------- |
| 扫描件（无文字层）                      | **不做 OCR**。P0 决策是「不接云端」，本地 Vision OCR 属于 P4/P5 的可选项。现在这类页返回 0 文本并明确报告「页面没有可提取的文本」 |
| Type0 + 无 `/ToUnicode` + 无嵌入字体 | **判定不可译**，不猜编码。实测《Python 核心编程》仅 2 页（封面）属于此类，已列入警告                                 |
| 合并单元格（rowspan/colspan）         | **未识别**，所有格子一律 1×1。真合并的表格会把内容拆到相邻格，这是当前最大的表格缺陷                                    |
| 无线表格（只靠底色/留白分区）                | **检不出**。算法只认矢量线；这类表格需要视觉模型，与全离线冲突                                                 |
| 竖排文字                           | 未处理。`Tm` 旋转能识别出 `angle`，但归并与分栏都按水平假设写                                             |
| 多栏 + 跨栏图注                      | 启发式。跨栏行按纵向位置归到栏上/栏下，夹在栏中间的单列处理                                                    |
| PDF 的 `/Rotate 90`             | 坐标仍是未旋转页面空间；阅读顺序未按旋转校正                                                            |
| 段落级 F1                         | **没有标注语料，不宣称**。只给可复核的字符召回与抽查结果                                                    |

## 6. 与 P3 的衔接

P2 的输出正好是 P3 的输入：

- 每个 `ILBlock` 有 `box`（段落框）、`fontSize`、`lines`、`text` → 排版引擎按框排译文；
- `ILTable` 有 `cells` → 单元格单独翻译、单独回填；
- `ILFigure` 有 `box` → 排版时锁定区域，不许文字压上去；
- `translatable=false` 的页直接进 `needsReview`，不静默跳过。

P3 要补的是「反向」：把译文排进这些框里（度量、断行、禁则、三档投放、overflow 出口）。  
P2 只负责「框在哪、里面是什么」。
