# P1 阶段报告：Form 递归驱逐 + 字体子集化 + 接管文本

> 日期：2026-11-23 08:5x
> 目标：证明「驱逐原文 → 用自带字体画上我们的字」这条链路成立。
> 结论：**成立**。中文在 PDFKit 里既能渲染也能逐字提取，同页图片字节不变。

---

## 1. 一句话结论

P1 的目的不是「多写几千行代码」，而是验证架构里最关键的那个假设：
**我们能不能在不碰图片和矢量的前提下，把原文换成自己的文字。**

能。证据是三条互相独立的检查同时通过：

| 检查 | 手段 | 结果 |
|---|---|---|
| 文字真的画出来了 | PDFKit 渲染 → 截图目视 | 宋体清晰，无豆腐块、无乱码 |
| 文字真的可提取 | PDFKit `page.string` | 20 个汉字逐字正确（说明 `/ToUnicode` 对） |
| 图片真的没动 | 逐对象 SHA-256 | 409 页书 533 张图、40 页文档 4 张图，全部相同 |
| 其余像素真的没动 | 150 dpi 逐像素比较 | 差异 0.299%，包围盒恰好等于插入文字的矩形 |

## 4. 踩到的坑

这一节比代码值钱，全部是「自造样本测不出来、只有真数据才会暴露」的类型。

### 4.1 `/XObject` 是内联字典时整页被跳过（静默失败）

第一版 `PDFFormCloner` 和 `rewritePageResources` 都写了：

```swift
guard case .reference(let xoRef)? = resources["XObject"] else { return nil }
```

而 PDF 里 `/Resources << /XObject << /Fm1 6 0 R >> >>` 是完全合法的**内联**写法。
于是「共享 form 需要克隆」这条逻辑直接返回 nil，既不克隆也不报错，
驱逐器落到「跳过」分支——表现是**目标页的文字没删**，但不报错。

是 `shared-form-clone-count`（期望 1，实际 0）这个断言抓到的。修法是统一走
`resolvedXObjects()`，引用与内联都认。

教训：**PDF 里几乎每个字典类条目都有「引用 / 内联」两种写法，只处理一种必然静默失败。**

### 4.2 实例化之后的字体里**没有复合字形**

原计划是「在字体里找一个复合字形，验证子集时组件编号被改写」。实测发现：

```
font-composite-survey  →  0 个复合字形
```

因为 `varLib.instancer` 在实例化可变字体时会把组件展开成简单轮廓（变体轴上组件的偏移也要插值，
展开比留着更简单）。**这不是 bug，是这个字体的正常状态。**

所以复合字形重编号改为用**合成字节序列**测试：手工拼一个 `numberOfContours = -1`
加两个组件的字节串，断言 `100 → 3`、`200 → 4` 且 flags/参数不动。
这样不依赖任何字体恰好含有复合字形。

顺带的好处：真实字体里没有复合字形，说明子集器在这条路径上的风险比预估更低。

### 4.3 `hmtx.lsb` 不能写 0

第一版子集器为了省事，把每个字形的 `lsb` 都写成 0。这在多数情况下看不出问题，
但部分光栅器会用它做 hinting 对齐，写 0 会让字形整体左右偏移半个像素到一像素——
小字号下表现为「字有点糊」，很难归因。

修法：解析 `hmtx` 时把 lsb 一起读出来，子集时按原值搬运。

### 4.4 「就地替换能省体积」是错的

一度以为把内容流写成新对象会让正文翻倍，改成就地替换后实测体积**一点没变**（还是 +344 KB）。

原因是**增量更新的固有成本**：旧内容流即使 xref 不再引用，字节仍然物理留在文件里。
所以「替换」和「新建 + 改 /Contents」对体积没有区别，只有对象数量不同。
真正的减法只能靠全量重写（`scrub`，P4）。

这个认知修正已经写进代码注释，避免以后又有人为了「省体积」去优化错的地方。

### 4.5 合成样本的构造器有 bug

测试里 `assemble(objects:streams:)` 只遍历 `objects` 列表，而内容流对象只出现在
`streams` 里 → 对象根本没被写进 PDF → 页面没有 `/Contents` → 驱逐「成功」但什么都没删。

表现是 3 个断言一起挂。修法：以 `objects ∪ streams` 的键为准，缺字典的自动补 `<< /Length n >>`。

### 4.6 字体生成不确定：`head.modified` 被刷新

`make-fonts.py` 第一版跑出来的 SHA-256 是 `63ab17ac…`，第二次跑变成 `d76dae65…`。
原因很普通但很致命：**`fontTools` 保存时默认把 `head.modified` 改成当前时间**。

后果链条：产物字节每次不同 → 锁 SHA-256 没意义 → 子集 golden 全部失效 →
「昨天还能过、今天过不了」这种最难查的失败。

修法：`font.recalcTimestamp = False`，保留源字体的 created/modified。
验证方式就是**连跑两次比较 SHA-256**，现在两次一致（`c254dd01…` / `0bce842c…`）。

这条已经写进 `make-fonts.sh` 的输出提示：产物入库，构建流程只校验不重生成。

### 4.7 用「旧印象」核对数据，差点误判为回归

`-1F平面布置图-1.pdf` 我第一次报告说「3 个 Form XObject 被跳过」，P1 跑出来是 0 个，看起来像回归。

查下去发现：该文件的最新修订里，页面 `/Resources` 指向的对象 17 就是一个**空字典 `<<>>`**
（`17 0 obj <<>> endobj`），文件里 13 个 Form 全部成了孤儿，图形全在 13 条内容流里内联绘制。
渲染检查：107,720 个非白像素，页面不空 —— 说明解析是对的，**「0 个 Form」才是正确答案**。

教训：**不要拿「上次跑出来的数字」当基准，要拿「可独立验证的事实」当基准。**
这次的验证手段是「渲染出来非白像素不为 0」，而不是「上次是 3」。

## 7. P2 的前置

P1 之后，「写」这一侧已经通了。P2 要补的是「读」：

1. **字符级文本提取**：解析 `Tf`/`Tm`/`Td`/`TD`/`T*`/`TL`/`Tz`/`Ts`/`Tj`/`TJ`，把每个字形落到页面坐标；
2. **`/ToUnicode` 反查**：这是拿到 unicode 的唯一可靠途径；没有就标记不可译，不猜；
3. **字体宽度表**：Type1 `/Widths`、CIDFont `/W`、TrueType `/Widths` 与 `/W`，用于断行与框宽估算；
4. **段落归并**：行 → 段（行距、字号、缩进、栏检测），这是版面启发式的核心；
5. **表格网格**：矢量线段聚类 + 行列一致性校验（Vision 不提供表格结构，这部分只能自研）。
