## 4. 在真实文件上才暴露的四个 bug（都修了，都留了回归用例）

这一节是本文最有价值的部分：**这四个问题在自造样本上全都测不出来。**

### B1. `compression_decode_buffer` 在缓冲不足时返回**非零的截断长度**

- **症状**：661 页的 PDF 解析出 `页数 0`，但 `xref 22573 条`（`/Size` 是 29147）。不报错、不崩溃。
- **根因**：xref 流解码后应有 200,655 字节，我初始缓冲给 154,648（`input.count * 8`），
  系统返回了 158,011 而不是 0，被当作「解码成功」→ 只填了 22573 行 → `/Pages` 指向的对象恰好落在缺失区间 → 页树为空。
- **修法**：把「返回值 == 容量」视为截断，扩容重试（`inflateRaw`）。
- **教训**：**「页数为 0」这种静默失败必须当成解析器 bug 排查**，不能当成文档问题。`pdf-dump` 现在会自动打印诊断。

### B2. zlib 头识别对了，却在 adler 不匹配时退回「整段当裸 deflate」

- **症状**：某 xref 流解压后预测器报「未知 PNG 行过滤器 124」。
- **根因**：我先判 zlib 头，解出内容后发现 adler32 不符（因为流里还有尾部填充），
  于是「保险起见」再试整段裸 deflate——而 `0x78` 会被解释成 stored block 头，解出一堆长度非零的垃圾，且不报错。
- **修法**：只要去了头能解出非空内容就采信 zlib 解释；adler 仅用于编码与测试，不再作为回退依据。
- **教训**：**"兜底再试一次" 是危险的**，尤其当两条路径都「成功」时。

### B3. 经典 xref 表 + `/Prev` 指向交叉引用流 → CoreGraphics 直接拒绝打开

- **症状**：我自己的解析器能读（`pdf-verify` PASS），但 PDFKit 打不开，
  `CG_PDF_VERBOSE=1` 给出 `failed to find start of cross-reference section`。
- **根因**：这份 PDF 1.6 文件用 xref **流**收尾，我在增量更新时统一写了**经典表**并把 `/Prev` 指回那个流。
  语法上合法（PDF 32000-1 §7.5.8.4 允许），但 CoreGraphics 的实现不接受这种混合。
- **修法**：读原文件最后一段的类型，是流就照样写**交叉引用流**（`/Type /XRef`、`/W [1 4 2]`、`/Index`、可选 Flate）。
  已加回归用例 `xrefstream-writes-xref-stream` / `xrefstream-reparse`。
- **教训**：**"我的解析器能读" 不构成正确性证明**，必须用独立实现（PDFKit/CoreGraphics）复核。

### B4. 自造测试样本自己也写错了（free 行 8 字节 vs `/W` 规定 7 字节）

- **症状**：新增的 xref 流用例崩溃在 `pages()[0]`。
- **根因**：`/W [1 4 2]` 规定每行 7 字节，我把 free 行写成了 8 字节，整张表错位。
- **价值**：这个 bug 反而说明 `pdf-dump` 的「页数为 0 诊断」有用——它当场指出了 `/Pages` 解析为 null。

另外两处小修（非本次功能引入，release 才报的警告）：
`SherryTokenizer.swift` 的未使用绑定与 `var printable` → `let`，**release 构建现已零警告**。

## 6. 与架构文档的偏差

1. **写回路径变成两条**（经典表 / 交叉引用流），架构文档里只写了「增量更新」。原因是 B3，属于实现细节，不影响设计。
2. **内容流重新压缩**：文档里写的是「新流写未压缩」，实测后改为「压得小才压」，661 页那份从 +7.74 MB 降到 +1.53 MB。
3. **`PDFEvictor` 允许零改动**：文档没考虑「整页无文本」的情况，实测 CAD 图纸就是这种。现在当正常情况处理并给出原因提示。
